# AGENTS.md — Системные правила и архитектурные ограничения GeoWeedStation

Данный документ регламентирует правила архитектуры, потоковой модели, работы с данными и лицензирования для всех разработчиков и AI-ассистентов проекта **GeoWeedStation**.

---

## 1. Архитектурные слои и поток зависимостей

Проект строго следует слоистой архитектуре:
```
[ UI (PySide6) ]
       │
       ▼
[ Controllers ] (координация потоков и сессий)
       │
       ▼
[ Workers / Network / Core / Schemas ]
       │
       ▼
[ Config / Entities ]
```

### Правила изоляции:
1. **Ядро (`core/`) и схемы (`schemas/`) НЕ ДОЛЖНЫ импортировать `PySide6`**.
   - Вся бизнес-логика (парсинг XMP, инференс ONNX, картографический движок `map_engine`, расчет планов миссий) обязана быть чистым Python кодом.
   - Запрещено использовать типы `QImage`, `QPixmap`, `QThread`, `QObject` и т.д. внутри `core/` и `schemas/`.
   - Это гарантирует тестируемость ядра без GUI и возможность запуска в CLI/серверном режиме.
2. **Контроллеры (`controllers/`)**: связывают пользовательский интерфейс с воркерами и сервисами, управляют состоянием и жизненным циклом фоновых операций.

---

## 2. Модель потоков и UI (PySide6)

1. **Главный GUI-поток (Main Thread) никогда не блокируется.**
2. Любые длительные и тяжелые операции выполняются **исключительно в фоновых воркерах (`QThread`, `QThreadPool`)**:
   - Сетевые вызовы REST API и скачивание файлов/архивов (`network/`);
   - Чтение и декодирование изображений/видео высокого разрешения через OpenCV;
   - Парсинг XMP-метаданных пачек снимков;
   - Нейросетевой инференс ONNX Runtime;
   - Тяжелые расчеты картографических матриц и KDE.
3. **Обмен данными между потоками:**
   - Передача данных из фоновых потоков в GUI допускается **только через Qt Signals & Slots**.
   - Передаваемые объекты должны быть иммутабельными DTO (Pydantic / dataclasses / numpy-массивы).
   - Воркеры должны поддерживать безопасное прерывание по флагу отмены без утечек памяти.

## 3. Архитектурные ограничения ТЗ

1. **XMP и метаданные:**
   - Извлечение пространственных параметров (координаты, высота, углы подвеса Yaw/Pitch/Roll, фокусное расстояние объектива) выполняется **ТОЛЬКО** из встроенных XMP-тегов изображений (`drone-dji`, `Camera`, `agro`).
   - Использование любых внешних sidecar-файлов (`.txt`, `.json`, `.xml` рядом со снимками) **строго запрещено**.
2. **Блокировка карты:**
   - При отсутствии пространственных тегов или при относительной высоте $H \le 0$ модуль цифрового картографирования обязан блокироваться с выводом штатного предупреждения оператору:
     *«Геопривязка отсутствует. Доступен только просмотр исходных изображений»*.
3. **Разделение систем координат:**
   - Поддерживаются две системы координат:
     - `local_aruco` (метры в полетной зоне полигона);
     - `wgs84` (глобальные широта/долгота, EPSG:4326).
   - Автоматическая конвертация между `local_aruco` и `wgs84` без явно заданной опорной базовой точки `wgs84_origin` **запрещена**.
4. **Сетевой клиент к борту БПЛА (`agrovision_onboard`):**
   - Таймаут любых REST API запросов (`/status`, `/start`, `/stop`, `/runs`) составляет **$\le 2.0$ с**.
   - При разрывах связи клиент обязан корректно обрабатывать сетевые ошибки и восстанавливать соединение с экспоненциальной задержкой (reconnect backoff).

## 5. Протокол разработки

- Задачи выполняются строго последовательно по дорожной карте `docs/tasks/README.md`.
- Каждая задача сопровождается модульными/интеграционными тестами в `tests/`.
- Перед сдачей задачи все автотесты должны быть зелеными, а статус задачи в `docs/tasks/README.md` обновлен на `[Completed]`.
